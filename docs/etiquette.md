# Open Source Etiquette

## Writing a good PR description

- State what the PR does and why, in one or two sentences at the top.
- Link the issue it resolves, if any (e.g. `Fixes #42`).
- If it changes behavior, say how you tested it.
- Keep the PR focused on one thing. A PR that fixes a typo and refactors an
  unrelated module is harder to review and more likely to stall.

## Responding to review feedback

- Review comments are about the code, not about you. Don't take them personally.
- If you disagree, explain your reasoning — don't just silently comply or
  silently ignore it. Reviewers usually have context you don't yet.
- If a comment is unclear, ask for clarification instead of guessing.
- Push new commits to address feedback rather than force-pushing over history,
  unless the maintainer asks you to squash — it's easier for reviewers to see
  what changed.

## Following the rules of the repo

- Read `CONTRIBUTING.md` before you start, not after your PR gets rejected.
- Match the existing code style, even if you'd write it differently.
- Read the code of conduct. It's not boilerplate — it's what maintainers will
  actually enforce.

## Communication norms

- Maintainers are often volunteers with limited time. A PR sitting for a few
  days without a response is normal, not a rejection.
- Ping (`@mention`) a maintainer at most once after a reasonable wait (a week
  or two for small projects), not repeatedly.
- If you can no longer finish a PR you started, say so in a comment — it's
  fine, and it frees up the issue for someone else.
- Say thank you. Maintainers remember contributors who are pleasant to work with.
